# Java Spring Boot ConfigMap + Secret + Sidecar Lab (NO CODE CHANGES)

## Reviewed source
Uploaded `java-applciation-main (3).zip`: source includes `src/main/resources/application.yml` with `${PORT}`, `${DB_URL}`, `${DB_USER}`, `${DB_PASSWORD}`, `${ADMIN_API_KEY}`, `${SEED_DEMO_DATA}`; Java admin controller enforces `X-Admin-Key`. Dockerfile runs the Spring Boot JAR as non-root. Source has no existing order-file creation routine.

## What this lab demonstrates
- ConfigMap dynamically supplies port, H2 database URL and log-file settings.
- Secret supplies the application's existing admin API key.
- A BusyBox sidecar reads an **actual Spring Boot log file** from a shared `emptyDir` volume and extracts Started/WARN/ERROR/DEBUG lines to `events.log`.
- No modifications to Java source, application.yml, Dockerfile, or published Docker image.

## Requirements
- Working Kubernetes cluster with permission to create Namespace, Deployments, ConfigMaps, Secrets and Services.
- `kubectl` configured and Docker Hub image `karthikeya91101/myapp:v2` pullable.
- Use an isolated namespace or avoid existing same-named deployments. These demo names are distinct from the source project's existing manifest names.

## Show genuine file processing in sidecar
```bash
kubectl -n globalshop logs deployment/globalshop-sidecar-demo -c log-processor --tail=30
kubectl -n globalshop exec deployment/globalshop-sidecar-demo -c java-app -- sh -c 'ls -l /shared/logs && tail -n 8 /shared/logs/globalshop.log'
kubectl -n globalshop exec deployment/globalshop-sidecar-demo -c log-processor -- cat /shared/logs/events.log
```
Expected: the sidecar captures a Spring Boot startup message containing `Started ` and any warning/error lines; events are filtered from the actual log generated by Java.

## Live ConfigMap update / restart
```bash
kubectl -n globalshop patch configmap globalshop-sidecar-config --type=merge -p '{"data":{"LOGGING_LEVEL_COM_GLOBALSHOP":"DEBUG"}}'
kubectl -n globalshop rollout restart deployment/globalshop-sidecar-demo
kubectl -n globalshop rollout status deployment/globalshop-sidecar-demo
kubectl -n globalshop exec deployment/globalshop-sidecar-demo -c java-app -- printenv LOGGING_LEVEL_COM_GLOBALSHOP
```
The new environment variable reaches **newly created containers**, not old running containers. `emptyDir` is fresh for a replaced Pod, so old logs/reports are lost.

## Live Secret rotation / restart
```bash
kubectl -n globalshop patch secret globalshop-sidecar-secret --type=merge -p '{"stringData":{"ADMIN_API_KEY":"rotated-classroom-admin-key"}}'
kubectl -n globalshop rollout restart deployment/globalshop-sidecar-demo
kubectl -n globalshop rollout status deployment/globalshop-sidecar-demo
```
Retest the admin API: old key should fail, new key should work. The key remains an example training credential. Avoid typing real secrets into shell history or Git.

## Why not an automatic order-file processor?
The current Java source persists orders to the database; it does **not** write order files. Kubernetes cannot force an unchanged Java application to create order-export files. A sidecar can process real **log files** automatically because Spring Boot supports file logging using an environment variable. For real order-file processing, the app must already write files to a shared location or use an external producer/exporter.

## Production limitations
- One replica with local H2 data is purely for teaching. Use a PostgreSQL service or managed database, plus durable storage for production.
- `emptyDir` is ephemeral. Use centralized logging and durable storage for reliable processing.
- This is a **regular second container** under `containers`, not a native Kubernetes sidecar under `initContainers`.
- K8s Secrets are not necessarily encrypted at rest; use proper RBAC, cluster at-rest encryption and external secret management as applicable.
- The sidecar filters logs and writes a local file; it does not ship alerts to a monitoring platform.
- Logging-related Spring Boot environment variable behavior is based on framework configuration. Docker Hub image build provenance and live Kubernetes execution have not been verified here.

## Troubleshooting
```bash
kubectl -n globalshop describe pods -l app=globalshop-sidecar-demo
kubectl -n globalshop logs deployment/globalshop-sidecar-demo -c java-app --tail=80
kubectl -n globalshop logs deployment/globalshop-sidecar-demo -c log-processor --tail=80
kubectl -n globalshop exec deployment/globalshop-sidecar-demo -c java-app -- printenv LOGGING_FILE_NAME
```
If Java fails with a permission-denied error writing `/shared/logs/globalshop.log`, examine the Pod `fsGroup` and CSI/cluster policies. If the sidecar never finds the log file, check the `LOGGING_FILE_NAME` variable and application startup. If both containers start but Java API fails, inspect application logs for database errors. If a Port-forward local port is already occupied, use `18080:80` and curl port 18080.
