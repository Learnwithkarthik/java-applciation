01 — THE PROBLEM MAVEN SOLVES

Imagine building GlobalShop manually.

Maven automates repeatable compilation, dependency downloads, testing and packaging. It creates a predictable build process developers and CI servers can share.

Beginner-friendly
✕ WITHOUT MAVEN

Every developer invents a build process

Manually find Spring libraries, download compatible JARs, set the classpath, compile the Java files, run tests, then package everything yourself.

1. Find dozens of dependency JARs
2. Fix library version clashes
3. Run javac with a long classpath
4. Bundle and test manually
✓ WITH MAVEN

One definition, same process everywhere

The pom.xml describes the project. Maven resolves dependencies, calls compiler/test/packaging plugins, and generates an artifact.

1. Define dependencies in pom.xml
2. Run mvn clean package
3. Tests run automatically
4. Find JAR under target/

03 — LOOK INSIDE THE ARTIFACT

What is a JAR file, really?

A Java ARchive packages compiled Java classes, resources and metadata into a ZIP-format archive. GlobalShop uses a Spring Boot executable JAR that also includes runtime dependencies and a boot loader.

Click files inside the imaginary JAR
JAR
globalshop-1.0.0-SNAPSHOT.jartarget/ · executable Spring Boot archive
A JAR is a packaged file, not a container and not a source-code repository.
UNDER THE HOOD

META-INF/MANIFEST.MF

The launch instructions.

The manifest contains metadata such as the Main-Class entry used by Java to start an executable archive. A Spring Boot JAR also identifies its application's start class.

Example

Main-Class points to Spring Boot's launcher; Start-Class points to com.globalshop.GlobalShopApplication.

RUN THE PACKAGED APPLICATION
java -jar target/globalshop-1.0.0-SNAPSHOT.jar
Why not run .java directly in production? A built, tested and versioned artifact provides a consistent deployable unit. The JVM executes bytecode in compiled .class files. A plain library JAR may not be runnable with java -jar; this one is built as a Spring Boot executable archive.
తెలుగులో: .java మనం రాసిన source code. Compiler దాన్ని .class bytecode గా మార్చుతుంది. అనేక class files, resources, libraries కలిపి .jar గా pack చేస్తాం. GlobalShop JAR ను java -jar తో execute చేయవచ్చు.
04 — PROJECT RECIPE VS PERSONAL SETTINGS

pom.xml vs settings.xml

Both are XML files, but they solve very different problems. pom.xml (not “pim.xml”) tells Maven what to build; settings.xml tells it how your particular environment connects to repositories.

pom.xml · shared in Git

The project's blueprint 🧩

Tracks project identity, Java version, libraries, build plugins and publish destinations. Maven reads it in the project root.

Click to explore a real GlobalShop configuration
  • groupId: company / package family
  • artifactId: application/library name
  • version: unique release or snapshot
  • dependencies: external libraries Maven retrieves

  
settings.xml · local/user or CI environment
The environment's access key 🔐
Contains Maven execution preferences: local repo path, mirrors and server authentication. Real credentials should not be committed to Git.
Click to explore the related settings
  • Default user path: ~/.m2/settings.xml
  • Global Maven path: $MAVEN_HOME/conf/settings.xml
  • Custom file: mvn -s path/to/settings.xml ...
  • Local dependency cache: ~/.m2/repository/

  
Security and accuracy: The project includes config/nexus-settings.example.xml as a safe example. It references environment variables (${env.NEXUS_USERNAME} / ${env.NEXUS_PASSWORD}), not hard-coded secrets. Use actual secrets only in your local environment or CI secret store. The server.id must match the target repository ID in pom.xml. A Nexus proxy/mirror is optional; it is different from the hosted repository used for uploads.
తెలుగులో: pom.xml ఒక team అందరికీ common: project dependencies, plugins, version. settings.xml developer/CI environment‌కు సంబంధించిన login, mirror, local repo settings. Password ను pom.xml లో పెట్టకూడదు.




05 — REAL-WORLD DEVSECOPS CONNECTION
How does the JAR reach Nexus?
Maven builds the artifact. Nexus stores and versions it so other jobs, developers and systems can retrieve the same artifact. Docker later packages the app with a runtime into a container image.
STEP 01
📋
pom.xml
Identifies com.globalshop:globalshop:1.0.0-SNAPSHOT and declares a snapshot deployment URL in the nexus-deploy profile.
STEP 02
🔑
settings.xml
Provides credentials for server ID nexus-snapshots via environment variables.
STEP 03
⚙
mvn deploy
Runs the necessary earlier lifecycle phases; the deploy plugin publishes artifact and metadata to the configured endpoint.
STEP 04
▤
Nexus Repository
Stores the versioned snapshot so a CI/CD deployment can retrieve that artifact instead of rebuilding manually.

  
Local install ≠ Remote deploy
mvn install → copies artifact into your machine's ~/.m2/repository. mvn deploy → uploads to a configured remote artifact repository such as Nexus. Neither means “deploy application to a server.”
Source code ≠ Artifact ≠ Image
GitHub holds source code. Nexus (Maven repo) holds JARs/POMs. Docker registry stores container images. Your Java app runs from a JAR, and a Docker image can include that JAR plus the Java runtime.
తెలుగులో: GitHub = source code store. Nexus = build అయిపోయిన JAR store. Docker registry = image store. install మన laptop లో, deploy remote Nexus లో; ఇది server మీద app run చేయడం కాదు.
