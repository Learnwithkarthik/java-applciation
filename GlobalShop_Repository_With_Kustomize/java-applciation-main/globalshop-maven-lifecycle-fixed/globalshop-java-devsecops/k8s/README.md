# GlobalShop Kustomize — Java 21 + Spring Boot + PostgreSQL

This folder was prepared specifically for:
`globalshop-maven-lifecycle-fixed/globalshop-java-devsecops`

## What was inspected (real application details)

- `Dockerfile`: multi-stage Maven / Eclipse Temurin Java 21, non-root JVM, port **8080**.
- `src/main/resources/application.yml`: environment variables `PORT`, `DB_URL`, `DB_USER`, `DB_PASSWORD`, `ADMIN_API_KEY`, `SEED_DEMO_DATA`.
- Spring Boot Actuator exposes `/actuator/health` and enables Kubernetes liveness/readiness probes.
- `compose.yml`: PostgreSQL 17 and Java application; DB is named `globalshop`.
- Admin UI `/admin.html` uses a **training-only** shared API key. Do not expose to the public Internet without real authentication.
- `DemoData.java` seeds the demo inventory once on an empty database. Parallel first-time startup may create a race.

## Architecture

```text
GitHub Actions (manual DEV or PROD)
  -> Maven Java 21 tests
  -> Docker build -> Artifact Registry image tagged with commit SHA
  -> render.sh: base + selected overlay + immutable image tag
  -> kubectl apply -k
  -> GKE namespace globalshop-dev or globalshop-prod
     |-- Service globalshop-app:8080 (ClusterIP)
     |-- Deployment globalshop-app (Spring Boot)
     |      |-- /actuator/health/liveness
     |      |-- /actuator/health/readiness
     |      `-- calls jdbc:postgresql://globalshop-postgres:5432/globalshop
     |-- Service globalshop-postgres:5432 (headless)
     |-- StatefulSet globalshop-postgres (1 replica)
     |      `-- PVC postgres-data-globalshop-postgres-0, 5Gi
     |-- ConfigMap generated by Kustomize (non-sensitive settings)
     `-- Secret globalshop-secrets (created separately, not committed)
```

## 1. Before doing anything: check your cluster

```bash
kubectl config current-context
kubectl get nodes
kubectl get storageclass
kubectl version --client
```

A **default dynamic StorageClass** is expected for the PostgreSQL 5Gi PVC.
If your iximiuz/kubeadm lab has no StorageClass, the PostgreSQL pod will remain Pending until you supply an appropriate PV/StorageClass. GKE usually supplies dynamic provisioning.
`kubectl kustomize` and `kubectl apply -k` are built into modern kubectl.

## 2. Preview manifests without deploying

From the `globalshop-java-devsecops` app folder:

```bash
kubectl kustomize k8s/base
kubectl kustomize k8s/overlays/dev
kubectl kustomize k8s/overlays/prod
```

A preview of these overlays uses the placeholder image `globalshop-app:local`.
**Do not apply the raw overlays** unless you have changed this placeholder to a real image.

## 3. Create namespace and Secret (repeat for DEV and PROD)

The application and PostgreSQL expect the *same database password* under the `DB_PASSWORD` key.
**Do not store secrets or the demo API key in Git.**

First create DEV:

```bash
kubectl create namespace globalshop-dev
```

In a safe local directory OUTSIDE the Git repository, create a private file
`globalshop-dev.secret.env` containing **your own strong values** (no quotes):

```text
DB_PASSWORD=REPLACE_WITH_A_STRONG_PRIVATE_DB_PASSWORD
ADMIN_API_KEY=REPLACE_WITH_A_LONG_RANDOM_PRIVATE_KEY
```

Create the Kubernetes Secret from that private file:

```bash
chmod 600 globalshop-dev.secret.env
kubectl -n globalshop-dev create secret generic globalshop-secrets \
  --from-env-file=globalshop-dev.secret.env
```

Securely delete the local copy after confirming the Secret was created. For PROD repeat
with **a different private file and credentials**:

```bash
kubectl create namespace globalshop-prod
chmod 600 globalshop-prod.secret.env
kubectl -n globalshop-prod create secret generic globalshop-secrets \
  --from-env-file=globalshop-prod.secret.env
```

The Secret must exist **before** the application or DB starts. If you rotate `DB_PASSWORD`
after PostgreSQL has initialized its persistent volume, rotating the Kubernetes Secret
alone will not change the PostgreSQL account password.

## 4. Build and publish the image (or use your already published image)

Your existing repo workflow builds from the correct directory. Example image:

```text
us-central1-docker.pkg.dev/YOUR_PROJECT_ID/docker-sample/globalshop-java:YOUR_TAG
```

To render the proper environment manifests while keeping the checked-in overlay unchanged:

```bash
bash k8s/scripts/render.sh dev \
  us-central1-docker.pkg.dev/YOUR_PROJECT_ID/docker-sample/globalshop-java \
  YOUR_TAG

kubectl kustomize k8s/runtime/dev
```

The resulting Deployment image should be your Artifact Registry image, **not** `globalshop-app:local`.

**DEV deploy:**

```bash
kubectl apply -k k8s/runtime/dev
kubectl rollout status statefulset/globalshop-postgres -n globalshop-dev --timeout=300s
kubectl rollout status deployment/globalshop-app -n globalshop-dev --timeout=300s
kubectl get pods,svc,pvc -n globalshop-dev
```

**PROD deploy (initially one web replica):**

```bash
bash k8s/scripts/render.sh prod \
  us-central1-docker.pkg.dev/YOUR_PROJECT_ID/docker-sample/globalshop-java \
  YOUR_TAG

kubectl apply -k k8s/runtime/prod
kubectl rollout status statefulset/globalshop-postgres -n globalshop-prod --timeout=300s
kubectl rollout status deployment/globalshop-app -n globalshop-prod --timeout=300s
kubectl get pods,svc,pvc -n globalshop-prod
```

The Kubernetes worker nodes need permission and network access to **pull the private image** from Artifact Registry.

## 6. Kustomize learning exercise: scale PROD only

First ensure the database has initialized and the initial PROD app pod is Ready
(the Java app's `DemoData.java` performs first-time product seeding).
Then edit `k8s/overlays/prod/kustomization.yaml`:

```yaml
replicas:
  - name: globalshop-app
    count: 3
```

Check without deploying:

```bash
kubectl kustomize k8s/runtime/prod | grep -A 3 'replicas:'
```

Apply and verify:

```bash
kubectl apply -k k8s/runtime/prod
kubectl get deployment globalshop-app -n globalshop-prod
kubectl get deployment globalshop-app -n globalshop-dev
```

DEV remains at one replica. Note the database stays at **one** PostgreSQL StatefulSet replica.
This is a learning setup, not a production-ready high-availability PostgreSQL architecture.

## 7. Connect GitHub Actions to GKE

Use the additional workflow at:

`.github/workflows/globalshop-kustomize-gke.yml`

GitHub -> Repository Settings -> Secrets and variables -> Actions -> **Variables**:

| Variable | Example |
|---|---|
| `GCP_PROJECT_ID` | Your Google Cloud project ID |
| `GCP_WIF_PROVIDER` | `projects/NUMBER/locations/global/workloadIdentityPools/POOL/providers/PROVIDER` |
| `GCP_SERVICE_ACCOUNT` | WIF-impersonated service-account email |
| `GCP_REGION` | `us-central1` |
| `GAR_REPOSITORY` | `docker-sample` |
| `GAR_IMAGE_NAME` | `globalshop-java` |
| `GKE_CLUSTER` | Actual GKE cluster name |
| `GKE_LOCATION` | Region or zone of the cluster |

Your existing `.github/workflows/gcp-auth.yaml` already uses the first three variable names.
Ensure the GitHub OIDC WIF provider condition permits this repository **and** the
workflow's GitHub Environment context. Some providers restrict the OIDC `sub` claim.

Configure GitHub **Environments** named `dev` and `prod`; add approval requirements
for `prod` if supported by your GitHub plan and repository visibility.

The CI/CD service account needs access to push Artifact Registry images, read the
GKE cluster credentials, and authorization to deploy to the cluster. In particular:
`roles/artifactregistry.writer` on the destination repository, GKE cluster viewing
capability, and appropriate **Kubernetes RBAC/IAM authorization** to manage the namespace's
Deployment, StatefulSet, Service, ConfigMap and PVC objects. Avoid blanket admin
privileges in long-term use.

**IMPORTANT**: Set up the target namespace and its `globalshop-secrets` Secret first,
as shown above. GitHub Actions does **not** generate or store database passwords.

GitHub -> **Actions** -> **GlobalShop - Kustomize Deploy to GKE** ->
**Run workflow** -> choose `dev` -> Run. After validating DEV, select `prod`.

The job does: checkout -> Maven verify -> WIF auth -> Docker build/push with commit SHA ->
GKE auth -> temporary Kustomize image overlay -> `kubectl apply -k` -> rollout checks.

The GitHub workflow's production selection builds the same Git commit again.
For mature releases, prefer **build once / promote exactly the same image digest**
rather than rebuilding the image for each environment.

## 8. Troubleshooting

| Symptom | Likely issue / command |
|---|---|
| `ImagePullBackOff` | Check Artifact Registry path, pushed image tag and node's Artifact Registry reader permissions |
| PostgreSQL `Pending` | `kubectl get pvc -n globalshop-dev`; check StorageClass/PV |
| Application stuck `Init:...` | DB not ready; `kubectl logs -n globalshop-dev statefulset/globalshop-postgres` |
| Application `CrashLoopBackOff` | `kubectl logs -n globalshop-dev deployment/globalshop-app --previous` |
| `CreateContainerConfigError` | Check `globalshop-secrets` and required keys |
| GKE deployment `Forbidden` | Check namespace-scoped Kubernetes authorization and identity |
| First PROD multi-pod startup race | Bootstrap with one web replica before changing to three |
| Running on iximiuz with no persistent storage | Provision a StorageClass/PV first; this package intentionally does not silently use ephemeral DB data |

## Environment and security notes

- Secrets are not generated as Kustomize `secretGenerator` literals, since real credentials
  should not end up in a committed file or copied manifest.
- This is an instructor-friendly **training deployment**.
- Production hardening still needs managed/external PostgreSQL or HA, database migrations,
  network policies, proper external admin authentication, TLS/Ingress, backup/restore,
  resource tuning, monitoring and a secure secret-management solution.
- The app's `spring.jpa.hibernate.ddl-auto=update` is **lab only**.
- No external IP / public Ingress is created by these files; use `kubectl port-forward`.
